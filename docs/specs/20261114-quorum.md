# quorum: a shared code pad for interviews

## Intent

quorum is a code pad for technical interviews. The interviewer opens a room by
URL, sends the link to a candidate, and both type into one code editor in real
time, seeing each other's cursors and selections with names.

It is a sibling of [kalyaka](https://github.com/tmshv/kalyaka) (a shared
drawing sheet) and keeps its spirit: no accounts, no storage, a room exists
only while someone is in it, the whole thing ships as one static binary, and
it is simple and fun to use. Unlike kalyaka, the front end is a real project
(package.json, TypeScript, Vite, vitest) and the server is written in Rust.

## Goals

- Rooms by URL: every single-segment path is a room (`/quiet-otter-42`). The
  front page suggests a random room name with a reroll button.
- One shared code document per room, edited concurrently without conflicts
  (CRDT).
- Live remote cursors and selections, labelled with each person's name and
  colour.
- A people list showing who is in the room.
- A random funny name per person per room; editable.
- Syntax highlighting with a room-wide language choice.
- Two editor themes from an existing collection (thememirror): Cool Glow
  (neon dark) and Rosé Pine Dawn (plain light).
- Copy the room link; copy or download the code.
- Hard caps on everything so server memory is bounded.
- One static binary with the built front end embedded; Linux and macOS
  release archives (amd64, arm64).
- MIT license.

## Non-goals (v1)

- Running code (no execution of any kind, not even in the browser).
- Accounts, roles (interviewer vs candidate), auth, room passwords.
- Persistence: nothing is written to disk, no history after a room empties.
- Chat, voice, video.
- Multiple files per room.

## Anti-goals

- Writing anything to disk or a database on the server.
- Saving a person's name in `localStorage`. A name lives in `sessionStorage`
  at most, scoped per room; the same person may have different names in
  different rooms.
- Inventing editor themes. Themes come from published theme collections.
- A heavy page: no Monaco, no UI framework.

## Constraints

- Behind a reverse proxy that terminates TLS (Caddy), same as kalyaka. The
  visitor IP is taken from the first `X-Forwarded-For` entry; the proxy must
  overwrite that header. WebSocket origin must match `Host`.
- The server can run with no user, no writable filesystem and loopback-only
  networking.
- The front end must be built (`npm run build`) before the Rust binary is
  built, because the binary embeds `web/app/dist`.

## Approaches considered

1. **Rust + yrs, server keeps each room's document in memory (chosen).**
   The server speaks the standard Yjs sync and awareness protocol through
   `yrs::sync`, so the client uses the stock `y-websocket` provider. Late
   joiners sync straight from the server; no peer-snapshot logic. Cost: the
   server holds room text in RAM, bounded by caps.
2. Rust relay that does not understand Yjs, with kalyaka-style snapshots
   from the longest-present peer. Simpler server, but needs a custom client
   provider and ports the snapshot dance. Rejected: more code, less standard.
3. Keep Go + centrifuge from kalyaka. Reuses a tested hub, but also needs a
   custom provider. Rejected: centrifuge adds nothing once Yjs has its own
   protocol, and the user prefers Rust when centrifuge is not required.

Editor alternatives considered: Monaco + Yjs (2-4 MB, workers, awkward to
theme, clunky remote cursors) and CodeMirror 6 + Loro (~1 MB WASM, needs
`wasm-unsafe-eval`, younger binding). CodeMirror 6 + Yjs was chosen.
`y-octo` (Rust Yjs port by AFFiNE) was considered instead of `yrs`; rejected
for v1 because it is v0.1.0, several features are in progress, and it only
provides protocol encoding without a server layer.

## Decided stack

### Server (Rust)

- `axum` + `tokio` for HTTP and WebSocket.
- `yrs` (0.28.x) with `yrs::sync` (`Awareness`, `DefaultProtocol`, `Message`,
  `SyncMessage`) for the Yjs sync and awareness protocol.
- `rust-embed` (or equivalent) to embed `web/app/dist`.
- A rate limiter crate (e.g. `governor`) for per-connection message rate.
- Cross-compiled with `cargo-zigbuild` to linux/amd64, linux/arm64,
  darwin/amd64, darwin/arm64.

### Front end (`web/`)

- Vite + TypeScript, no UI framework. npm with a committed lockfile.
- npm workspaces, splitting core from app logic:
  - `web/package.json`: workspace root (scripts: build, test, typecheck).
  - `web/core` (`@quorum/core`): no DOM UI. The collaborative editor
    setup (Yjs doc, provider wiring, `y-codemirror.next` extensions),
    language registry, theme registry, name and room generation,
    normalisation and sanitising. Most unit tests live here.
  - `web/app` (`@quorum/app`): the Vite app. Home view, top bar, people
    list, menus, wiring core into the page. Builds to `web/app/dist`,
    which the binary embeds.
- CodeMirror 6 + `y-codemirror.next` (stable, Yjs v13 line; not the unstable
  `@y/codemirror` / Yjs v14 branch).
- `yjs` + `y-websocket` (stock `WebsocketProvider`).
- vitest for unit tests.
- Themes from `thememirror` (CodeMirror 6, no React), exactly two, chosen
  by the user:
  - **Cool Glow**: the neon dark theme, and the default.
  - **Rosé Pine Dawn**: the plain light theme.
  - The theme package's license is noted in the README.
- Languages, each loaded lazily (dynamic import) so the first page stays
  small:

  | Language                       | Source                                  |
  | ------------------------------ | --------------------------------------- |
  | JavaScript, TypeScript         | `@codemirror/lang-javascript`           |
  | Python                         | `@codemirror/lang-python`               |
  | Go                             | `@codemirror/lang-go`                   |
  | Rust                           | `@codemirror/lang-rust`                 |
  | Java                           | `@codemirror/lang-java`                 |
  | C, C++                         | `@codemirror/lang-cpp`                  |
  | SQL                            | `@codemirror/lang-sql`                  |
  | JSON, GeoJSON                  | `@codemirror/lang-json`                 |
  | CSS                            | `@codemirror/lang-css`                  |
  | HTML                           | `@codemirror/lang-html`                 |
  | Swift                          | `@codemirror/legacy-modes` `swift`      |
  | Kotlin, Objective-C            | `@codemirror/legacy-modes` `clike`      |
  | Bash                           | `@codemirror/legacy-modes` `shell`      |
  | Protobuf                       | `@codemirror/legacy-modes` `protobuf`   |
  | Plain text                     | none                                    |

  Highlighting is CodeMirror's own (Lezer grammars and legacy stream
  modes); no third-party highlighter. GeoJSON is JSON highlighting with a
  `.geojson` download extension.

## How it works

### URLs and HTTP

| Path                 | Serves                                            |
| -------------------- | ------------------------------------------------- |
| `/`                  | the app; shows the home view (random room name)   |
| `/<room>`            | the app; joins the room                           |
| `/ws/<room>`         | WebSocket, Yjs sync + awareness protocol          |
| `/assets/*`          | Vite build output (hashed names, cached for long) |
| `/robots.txt`        | allow `/` only, disallow rooms                    |

- Room name: `[a-z0-9][a-z0-9-]{0,39}`, same as kalyaka. The client
  normalises whatever is typed in the URL the same way kalyaka does.
- Paths with more than one segment (other than the above) return 404.
- `index.html` is served `no-cache`; hashed assets are cached for long.
- A strict Content-Security-Policy like kalyaka's. CodeMirror injects style
  elements; use CodeMirror's `EditorView.cspNonce` with a per-response nonce
  rather than `style-src 'unsafe-inline'`, if practical (builder's call).
- `--listen` flag (default `127.0.0.1:20481`), `--version` flag. The
  version comes from the git tag, passed in as an environment variable at
  build time (falls back to `dev`).
- Linux release builds target musl so they are fully static; macOS builds
  link the system libc, as every macOS binary must.

### Rooms and sync

- A room is created on first WebSocket connection to `/ws/<room>` and holds
  one `yrs::Doc` plus one `Awareness`. When its last connection closes, the
  room and its document are dropped.
- Each connection runs the standard y-websocket message loop: sync step 1/2,
  updates, awareness updates, awareness queries. Document updates and
  awareness updates are broadcast to the other connections in the room.
- When a connection closes, the server removes the awareness states that
  connection announced (track the Yjs client IDs seen on each connection) and
  broadcasts the removal, so cursors vanish immediately.
- Because `y-websocket` re-runs sync on reconnect, a client that is still
  open after a server restart pushes its copy back into the new empty room.
  This is accepted behaviour, not a feature to rely on.

### Shared state in the Yjs document

- `Y.Text("code")`: the code.
- `Y.Map("meta")`: `lang` (the room's language id). Changing the language
  changes it for everyone. A client sets a default `lang` only if it is
  still empty after its first sync, so first joiners do not overwrite each
  other.

### Awareness state (per person)

- `user: { name, color, colorLight }`, used by `y-codemirror.next` to draw
  labelled cursors and selections.
- Cursor and selection are written by `y-codemirror.next`.

### Names

- People get a whole name picked from one list of computing, ML and
  distributed-systems terms that sound like a funny nickname. The user gave
  the idea and examples; the list below extends it in the same spirit and
  lives in `@quorum/core`, easy to grow. Names are plain ASCII so they
  slugify cleanly into room names.

  Not Found, Sandbox Violation, Kernel Panic, Side Effect, Memory Leak,
  Round Robin, Access Denied, Access Granted, Read Only, Attention Layer,
  Null Pointer Exception, Undefined, Undefined Behavior, Deadlock,
  Race Condition, Consensus Algorithm, Lost Context, Not a Number,
  Bad Gateway, Gateway Timeout, Segmentation Fault, Random Forest,
  Decision Tree, Gradient Descent, Vanishing Gradient, Overfitting,
  Hallucination, Prompt Injection, Context Window, Off By One,
  Infinite Loop, Stack Overflow, Buffer Overflow, Heap Corruption,
  Dangling Pointer, Zombie Process, Orphan Process, Fork Bomb, Core Dump,
  Cache Miss, Cache Invalidation, Merge Conflict, Detached Head,
  Force Push, Magic Number, Spaghetti Code, Technical Debt, Rounding Error,
  Bit Flip, Garbage Collector, Cold Start, Edge Case, Rubber Duck,
  Byzantine General, Split Brain, Eventual Consistency, Dirty Read,
  Phantom Read, Lazy Evaluation, Busy Wait, Spin Lock, Callback Hell,
  Unhandled Rejection, Promise Pending, Syntax Error, Type Mismatch,
  Heisenbug, Works On My Machine.

- A generated name avoids names already in the room: once the first
  awareness states arrive, if the auto-picked name is taken (and the person
  has not edited it), it is re-picked from the free ones. If all are taken,
  duplicates are allowed.
- Room names come from the same list, slugified with a two-digit number:
  `kernel-panic-42`, `null-pointer-exception-07`.
- The name and colour are kept in `sessionStorage` under a per-room key, so a
  reload in the same tab keeps them, and another room or another tab gets a
  new one. Never `localStorage`.
- Editable from the people list. The server relays awareness updates
  untouched (no decode-edit-re-encode); it only caps the size of each
  person's awareness state (e.g. 4 KB). The client sanitises every name it
  displays: strips control and format characters, collapses whitespace,
  caps at 32 characters, falls back to "anonymous".
- Colour is picked from a fixed palette, avoiding colours already used in the
  room when possible.

### Per-viewer preferences

- Theme choice is per viewer and saved in `localStorage` (it is not a name).
- Default theme: Cool Glow.

### UI

A top bar and the editor filling the rest of the screen:

```
┌──────────────────────────────────────────────────────────────────────┐
│ quorum / brave-otter-42  [copy link]   lang: [Python ▾]  theme: [▾]  │
│                                   ● Brave Otter (you) ● Calm Lynx    │
├──────────────────────────────────────────────────────────────────────┤
│  1  def two_sum(nums, target):                                       │
│  2      seen = {}       ▌Calm Lynx                                   │
│  3      for i, n in enumerate(nums):                                 │
│  ...                                                                 │
└──────────────────────────────────────────────────────────────────────┘
```

- Top bar chrome (backgrounds, text, accents) follows the active editor
  theme's colours so the whole page matches.
- Copy code and download code (file extension from the language) in a small
  menu.
- Connection status shown subtly (connected / reconnecting / room full).
- The home view: a big room name input prefilled with a random name, a reroll
  button, and a go button. Same layout spirit as kalyaka's home page.
- Fun touches like emoji reactions are the builder's call; keep them small.

## Limits (hard caps)

| Limit                       | Value                     |
| --------------------------- | ------------------------- |
| Connections in total        | 1000                      |
| Connections per IP          | 8                         |
| Rooms                       | 200                       |
| People per room             | 16                        |
| Incoming WebSocket message  | 1 MB                      |
| Document size per room      | 1 MB (encoded state)      |
| Message rate per connection | 30/s, burst 60            |
| Name length                 | 32 characters             |
| Room name                   | `[a-z0-9][a-z0-9-]{0,39}` |

- Over-the-cap connections are refused before or right after the upgrade with
  a WebSocket close code the client can show ("room full", "too many
  connections").
- An update that would grow the document past its cap is rejected and the
  connection is closed with a dedicated close code. The client does not
  auto-reconnect on that code (the stock provider would otherwise resend
  the same update in a loop) and shows a "document too large" message.
- A client that keeps exceeding the rate limit is disconnected.
- A slow reader's outgoing queue is bounded; past it, the connection is
  dropped.
- Exact values may be tuned by the builder; the point is that every
  dimension of memory is capped.

## Developer workflow

- `just dev`: Vite dev server proxying `/ws` to a running Rust server.
- `just test`: `cargo fmt --check`, `cargo clippy`, `cargo test`, `npm test`
  (vitest), `tsc --noEmit`.
- `just build`: `npm ci && npm run build` in `web/`, then `cargo build
  --release`.
- `just dist`: cross-compiled archives and SHA-256 checksums.
- `just release patch|minor|major|X.Y.Z`: same tag-driven flow as kalyaka.
- CI on pull requests and pushes to the main branch; a release workflow on
  tags publishes archives for the four targets.
- `cargo install` from git will not work without building `web/` first; the
  README says so. Release binaries are the supported install path.

## Testing

- Rust: room lifecycle (create, join, leave, drop on empty), every cap,
  awareness cleanup on disconnect, and an end-to-end test where two `yrs`
  clients connect over a real WebSocket and converge on the same text.
- Front end (vitest): name and room generation and normalisation,
  sessionStorage scoping of names, theme registry, language registry,
  name sanitising.
- Manual check: two browsers in one room typing at once, cursors visible,
  late joiner sees current text, language change propagates.
